When a keyword baseline beat my LLM

My LLM-based skill extractor won on the data I built it with, then lost on data it had never seen. Here is how I found out, and why I shipped the simpler method.

The setup

AlignED compares what graduate computing programs teach with what employers ask for. Both sides are mapped onto the O*NET skill taxonomy, so the first job is skill extraction: given a course description or a job posting, which O*NET skills does it mention? I built two extractors. One is a keyword and phrase matcher. The other uses an LLM with embeddings.

The result that looked like a win

On the 104 items I used while building, the LLM method scored higher: F1 0.426 against 0.364 for the keyword baseline. That is the number I could have stopped at. But the similarity cutoff for the LLM method was tuned on those same 104 items, so the comparison favored it from the start.

The test that changed my mind

I built a held-out set of 50 fresh items, labeled before either method ran, with the code frozen by hash. I also checked for leakage by comparing every held-out item with every development item by 8-word overlap. The largest overlap was 14.8%, which is boilerplate-level, and none reached my 30% screening threshold.

SetItemsKeyword F1LLM + embeddings F1
Development1040.3640.426
Held-out500.311 (0.234 to 0.377)0.198 (0.125 to 0.270)

On the held-out set the order reversed. A paired bootstrap puts the 95% interval for the difference (LLM minus keyword) at -0.177 to -0.046, which excludes zero.

What I did about it

I used the keyword method for the full-scale pipeline. It scored higher on the fresh test, and it is much faster and cheaper to run. I also changed how I report results: the development number is labeled as optimistic, and the held-out number is the one I quote.

What I would not claim

  • Fifty items is small. The intervals are wide. A larger labeled set is the obvious next step.
  • The labels are not independent. They were AI-drafted and checked by one human, not double-annotated.
  • Both methods have low recall (about 0.2 and 0.1), partly because the O*NET vocabulary has no entry for subjects such as machine learning. A larger skill vocabulary would help both.

What I took from it

Start with a simple baseline, and keep the test data away from tuning. The more sophisticated method is not wrong in general. It only has to earn its place on data it has not seen, and here it did not.
